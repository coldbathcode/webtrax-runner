# @webtrax/suite-links

Links suite (C05.4). Reads the crawl's link outcomes and edges (`SiteState`); makes no requests. Rules and their fix guidance are in `LINK_RULES` (`src/index.ts`), each `RuleMeta` v1.

- One finding per broken target **and** source page; the fingerprint is per target, so the cloud groups the source pages as occurrences.
- `resolveOutcome` follows a redirect the engine stopped at a known page through that page's own result (effective status, total hops). A redirect that ends broken is reported as broken, not as a chain; a chain is > 2 hops.
- A URL only in the sitemap that errors is `links.sitemap.stale` (low, per rebuild/08), not `links.broken.internal` as v1 reported it.
- Rate-limited and robots-skipped targets are never broken (`linkProblem` in the engine); a host that stayed rate limited gets one `links.host_rate_limited` info finding.
- **Links by device over HTTP (C06.10 slice b):** `links.scheme.invalid` (low, `schemeProblem`: a `tel:`, `sms:` or `mailto:` link whose number or address cannot work; one per link per page). `links.device.response_differs`: the 10 shallowest pages (`config.device_sample`) are asked for again as a phone and as a desktop browser (`ctx.requestAs`, the browser's user agent plus the Webtrax token); medium when one of them gets an error where Webtrax got 200. Links Webtrax was refused (401, 403, 406, 429, 503; up to 20) are asked for as a desktop browser, and one that then works is an info finding: a bot wall, probably not broken (the `links.broken.*` finding is still raised: V2-COR-03 is not settled here). `links.app.association_invalid` (medium, `associationProblems`): `/.well-known/apple-app-site-association` and `assetlinks.json` when present and not the site's HTML shell (redirected, wrong content type, not JSON, wrong shape), and a missing `assetlinks.json` when a page declares an `android-app://` alternate. Tests in `test/device.test.ts`.
- **Links by device, rendered (C06.10 slice c):** from `site.rendered` in `onSite`. `links.device.unreachable_on_phone` (medium, `unreachableOnPhone`): a working internal page a desktop visitor can click through to from the start page and a phone visitor cannot, linked usably at desktop on a page also loaded as a phone. Each visitor walks the crawl's links; on a page loaded at their size only the links usable there count; elsewhere the crawled links count, minus layout links (from more than half the pages, self links left out) the phone could not use on any page it loaded. When the crawl was incomplete (`site.incomplete`, set by the engine before `onSite`) only those layout links are reported. Found on astro.build with a page-by-page comparison: pagination numbers hidden on phones, reachable by Next; the walk does not report them. Evidence `linked_at_desktop_from`, `phone_pages_checked`, `in_site_menu`. Hosted scans load only the home page as a phone, so it judges the home page's menus. `links.device.covered` (medium): one per page and covering element, with every profile it was seen in. Tests in `test/rendered.test.ts` (real Chromium; mutation-checked: no menu opening, no hit test).
- Not yet: `links.anchor.missing`, `links.asset.broken` (browser stage / asset checks, C05.10).
