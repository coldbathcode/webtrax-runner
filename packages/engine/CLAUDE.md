# @webtrax/engine

The crawl engine (C05.3): v1's crawl loop rebuilt as the single-fetch pipeline (`plan/05-runner/pipeline-and-suite-contract.md`). `crawl(spec, deps)` takes a `JobSpec`, writes protocol records to a `Sink` (run → pages → summary) and returns the `SiteState` (pages, link outcomes, link edges, robots, sitemaps) for site-level suites.

- **One fetch per URL.** Internal links are answered by the linked page's own crawl result; only links the crawl won't visit (external, past `max_pages`/`max_depth`, excluded) get a link check (HEAD, then GET on 403/404/405/501), once each. Page redirects are followed hop by hop and stop at a page the crawl already has. The 5xx/timeout retry-once (v1 semantics) is the only repeat. `test/golden.test.ts` asserts this against the server's request log.
- **Requests** only through `src/requester.ts` (host throttle, timeout tied to the job signal, WebtraxBot headers, retries, Retry-After) on top of `@webtrax/net-guard`. Never call fetch directly.
- **Politeness:** `HostThrottle` is shared per process (`sharedThrottle`): 1/rps or robots Crawl-delay (≤ 30 s), whichever is longer, halved per 429; slots reserved synchronously (COR-09). 429 and 503+Retry-After wait and retry, then end `rate_limited`, never broken (COR-12).
- **robots.txt:** disallowed URLs are never requested (v1 HEAD-checked them); recorded as `robots_disallowed`.
- **Start URL:** same-site redirects are adopted as the origin (COR-01); unreachable → `failed/start_url_unreachable`; another site → `failed/start_url_redirects_offsite`, without fetching it.
- **Stopping:** caller abort → `partial/canceled` at once; time budget → stop the frontier, drain in-flight work up to `drainMs`, `partial/time_budget`.
- **Order** is breadth first, then by URL (`Frontier`), so page order is identical across runs at concurrency 1.
- **Suites** (`src/suite.ts`, C05.4): `deps.suites` lists the suites available; the spec's `suites` decides which run. Rules are validated at the start (must belong to the suite, declared once). `ctx.emit` fills suite, rule version, default severity, title and fingerprint, dedupes per fingerprint and source page, and writes the finding; the summary counts distinct fingerprints by severity. A suite that throws is recorded in `suiteErrors` and the crawl continues. Suites never fetch on their own: `ctx.request` is one guarded GET without following redirects. Canonical links are crawled or checked like links (edge kind `canonical`).
- **Optional browser hooks:** the browser stage runs only when an active suite both `requires: ['browser']` and defines `onBrowserPage`. A suite that defines `onBrowserPage` without requiring the browser (the AI suite's JavaScript-only check) joins that stage for its own sample of pages, and never starts Chromium by itself.
- **Browser profiles (C06.10 slice a, `src/profiles.ts`):** `spec.browser.profiles` (default `['desktop']`); `phone` is Chromium with a 412 x 915 touch viewport, Chrome for Android's user agent plus the Webtrax token, CPU 4 times slower (CDP) and a slow 4G line (1.6 Mbit/s down, 750 kbit/s up, 150 ms) shaped by the egress proxy. One browser and one proxy per profile. Every suite sees the first profile; suites with `everyProfile` (performance) also see the others, on at most `browser.extra_profile_pages` pages. Metrics carry `profile`. With several profiles the stage's findings are held and written once each when it ends, with `evidence.profiles` and the worst severity: the profile is never part of a fingerprint.
- **`deps.onHomePage`:** called with the start page loaded in Chromium, after the suites have seen it (for a caller that wants the rendered page, such as a thumbnail). It starts the browser stage by itself, then for the start page only: suites with optional browser hooks stay out. An error is recorded as a suite error (`engine`, `onHomePage`) and never fails the run.
- **Auth headers:** `spec.auth.headers` (plain strings; secret references must be resolved by the spec's builder) go to the start URL's origin only: through net-guard's `originHeaders` for HTTP, and a `context.route` on that origin in the browser stage, never to third parties. The run record keeps the spec with auth values `[redacted]` (`redactAuth`), so they never reach run.ndjson or a report. `auth.basic` and `auth.cookies` are not used yet.
- The golden fixture is `runner/fixtures/site/server.mjs` (moved from v1, which still uses it). Behaviour and mutation-checked rules: see `test/`.
