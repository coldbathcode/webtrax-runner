# runner/ (open source, Apache-2.0)

The Webtrax runner, CLI and local MCP server (MASTER_PLAN C05). Public since the alpha as `coldbathcode/webtrax-runner` (ADR 0010, D16). **This directory stays the source of truth** (ADR 0011): commit here, then `scripts/sync-runner.sh --push` mirrors each commit that touched `runner/` to the public repo with the standard workspace files added. Never commit to the public repo directly (the sync refuses when its HEAD matches no commit here). Keep runner commits separate from other work: their messages become public, and the sync refuses messages with an email address or a private identifier. The ordered steps, with what to read and "done when", are in [`plan/BUILD-PLAN.md`](../plan/BUILD-PLAN.md) Phase 1; status is in `TRACKER.md`.

- **Imports nothing outside `runner/`:** no cloud package (`@webtrax/domain`, `@webtrax/db`, `@webtrax/config` …), no relative path, tsconfig or file read that climbs out. `test/independence.test.ts` enforces it. Shared things the cloud also needs (protocol, bot identity) live here and the cloud imports them.
- **Own toolchain:** `tsconfig.base.json` and `eslint.base.js` here; packages extend `../../tsconfig.base.json` and use `runner()` from `../../eslint.base.js`. Every `package.json` says `"license": "Apache-2.0"` (tested).
- **Packages:** `packages/<name>`, published as `@webtrax/<name>` at the alpha. They stay `"private": true` until C05.9. The executor is `@webtrax/engine` (`@webtrax/core` is the cloud's).
- **Behaviour reference:** v1's crawler in `apps/legacy/runner/lib/` (`crawl-core.js`, `address.js`, `guarded-fetch.js`) and its tests. Port semantics exactly unless the plan says otherwise.
- **Commands:** `pnpm --filter './runner/**' test`, or `pnpm run check` at the root (the pre-push hook) which includes these packages.
- **Public-repo files, dormant here:** `action/` (the GitHub Action, tested in the public repo's CI, job `action`, against the fixture with the local CLI build; the monorepo's CI is Woodpecker, which cannot run Actions), `.github/workflows/ci.yml` and `release.yml`. GitHub only reads the monorepo's root `.github`, so they run in the public repo only.
- **Container image** (`Dockerfile`, H1; slimmed in H7): `scripts/image.sh [tag]` packs the CLI and builds on `node:22-bookworm-slim` with only Chromium's headless shell, installed by the CLI's own `playwright-core` (so they cannot drift; 330 MB against 908 MB on the Playwright base); `scripts/image-test.sh [tag]` proves it: version, non-root, and a `--browser` fixture check inside it (read-only root, no network) gives the same findings as outside. Both CIs run them. npm and corepack are removed from the image after the install (unused at runtime; the npm bundled with Node carried Trivy's only findings). **Published by `.github/workflows/image.yml`** (C05.11) on a `vX.Y.Z` tag: `ghcr.io/coldbathcode/webtrax-runner` for linux/amd64 and linux/arm64, tagged version, minor, major and latest, after `image-test.sh` and Trivy (fixable critical or high fails) pass on the exact amd64 build; SBOM and SLSA provenance attached; the digest signed with keyless cosign. Run it by hand for a dry run (no push, no signature). `scripts/image.sh --pack-only` packs the CLI for it.
- **Releasing:** bump `packages/cli/package.json`, commit, sync, then push a `vX.Y.Z` tag to the public repo. `release.yml` checks, builds, publishes to npm with provenance through npm trusted publishing (OIDC; no npm token exists, and none should be added), moves the major tag (`action@v0`) and creates the GitHub release.
- **Fixtures:** `fixtures/site/rules.mjs` (every HTTP rule on made-up hosts behind `virtualFetch`, goldens with fingerprints and the score, `test/rules-fixture.test.ts`) and `fixtures/site/browser.mjs` (every browser-stage rule in real Chromium on local servers: six axe rules, the four performance rules made slow by more than timing noise, `render.js_only`, the two device-link rules; clean twins; `test/browser-fixture.test.ts`, golden `fixtures/expected/browser-findings.json` of rule, path and severity, without fingerprints (they carry the port) or performance severities (machine speed)). A new browser-stage rule needs a page in `browser.mjs` (`MEASURE_DEFECTS`) or a reason in `rules-fixture.test.ts` `NOT_HERE`.
